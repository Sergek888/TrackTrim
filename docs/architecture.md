# Архитектура TrackTrim

## Назначение

TrackTrim — приложение для работы с геоданными независимо от их источника, формата и способа отображения.

Архитектура строится вокруг связки:

```text
геоданные
→ рабочая область
→ карта
→ действия пользователя
```

Конкретные сущности могут меняться (`Track`, маршрут, коллекция, анализ, слой карты), но архитектурные принципы должны оставаться неизменными.

---

# Основные принципы

## Предметная модель независима от источников

Внешние системы, форматы файлов, API и UI не определяют устройство предметной модели.

Внешние данные адаптируются к модели проекта, а не наоборот.

## Крупные зоны ответственности изолируются

Проект разделяется на независимые области:

* предметная модель;
* файловые форматы;
* внешние интеграции;
* рабочая область;
* карта и UI;
* серверные runtime-адаптеры.

Изменения в одной области не должны требовать изменений в остальных.

Изменение GPX не должно требовать изменения Komoot.

Изменение карты не должно требовать изменения модели.

Добавление нового источника не должно требовать изменений в общих UI-компонентах.

## Границы строятся по причинам изменения

Модуль выделяется тогда, когда у него появляется собственная причина изменяться.

Размер файла, количество строк или желание «навести порядок» сами по себе не являются причиной для создания новой сущности.

## Простота важнее формальной чистоты

Один понятный модуль лучше нескольких абстракций без самостоятельной ответственности.

Не следует вводить новые слои, сервисы, фабрики, registry, event bus или универсальные pipeline без существующей задачи, которую они действительно упрощают.

Прямой вызов между слоями с разрешённой зависимостью предпочтительнее цепочки посредников без собственной ответственности.

## Не скрывать связанность

Интерфейс или промежуточный слой не устраняют связанность сами по себе.

Если модули знают внутренние детали друг друга и изменяются совместно, искусственное разделение может увеличить сложность вместо её уменьшения.

Связанность должна быть либо признана и локализована, либо устранена изменением ответственности.

## Новая сущность появляется под давлением задачи

Новая сущность или архитектурная граница создаётся только если:

* поведение не относится к существующей сущности;
* существующий модуль начинает нарушать свою ответственность;
* новая граница локализует изменчивость или устраняет реальное дублирование;
* стоимость новой сущности меньше получаемой пользы.

## Универсальность и рост

Общие интерфейсы и контракты создаются на основе реальных сценариев использования.

Интерфейс должен быть ориентирован на рост системы, но не содержать параметры, режимы и возможности, используемые только одной реализацией.

Абстракция создаётся после появления устойчивого повторения.

Простая реализация предпочтительнее преждевременной универсальности.

# Потоки данных

Основной поток:

```text
External data
→ integration or format adapter
→ TrackSource
→ TrackMeta / Track
→ TrackLibrary
→ UI
```

Локальные файлы:

```text
File
→ LocalFileTrackSource
→ GpxConverter
→ Track
→ TrackLibrary
→ UI
```

Внешние системы:

```text
External API
→ integration library
→ TrackSource adapter
→ TrackMeta / Track
→ TrackLibrary
→ UI
```

---

# Направление зависимостей

```text
ui
→ application
→ model

application
→ formats
→ integration libraries

formats
→ model data contracts

integration libraries
→ own DTO and transport contracts
```

Запрещённое направление важнее структуры каталогов.

* `model` не зависит от UI, HTTP, форматов и внешних сервисов;
* `formats` не зависят от UI и пользовательских сценариев;
* интеграции не зависят от UI и внутреннего состояния приложения;
* UI не содержит предметных вычислений.

---

# Model

`model` содержит предметную модель и универсальные вычисления по геоданным.

Она может:

* рассчитывать расстояние, длительность, скорость и набор высоты;
* хранить накопленные значения;
* находить ближайшие точки;
* создавать сегменты и производные объекты;
* выполнять универсальный анализ геометрии.

`model` не знает о GPX, XML, HTTP, Komoot и UI.

Если понятие отражает реальную сущность предметной области, оно должно быть явно представлено в модели.

Технические детали транспорта, UI и форматов не становятся сущностями модели.

## Track

`Track` является неизменяемым.

Точки не изменяются после создания.

Анализ, сегментация и будущие операции редактирования создают новый `Track`.

Исходный объект не мутируется.

## TrackMeta

`TrackMeta` является паспортом объекта во внешнем источнике.

Он может существовать отдельно от геометрии и содержать имя, цвет, состояние загрузки и идентификатор во внешней системе.

Связь `TrackMeta` с `TrackSource` является осознанным компромиссом текущей архитектуры.

---

# Formats

`formats` отвечают только за чтение и запись внешних форматов.

Они преобразуют данные формата в модели проекта и обратно.

Форматы не управляют отображением, загрузкой или пользовательскими сценариями.

Текущая реализация:

```text
GpxConverter
```

---

# Integrations

Интеграция с внешней системой должна состоять из:

```text
integration library
+ TrackSource adapter
```

Интеграционная библиотека отвечает за:

* API;
* DTO;
* транспорт;
* авторизацию;
* ошибки;
* особенности внешней системы.

Она не должна знать о UI, `TrackLibrary` или внутренней структуре приложения.

Текущая реализация:

```text
src/komoot
```

---

# Application

`application` связывает модель, форматы, интеграции и UI.

Здесь находятся пользовательские сценарии, `TrackSource` и `TrackLibrary`.

## TrackSource

`TrackSource` представляет источник данных и отвечает за:

* загрузку списка объектов;
* загрузку геометрии;
* экспорт в поддерживаемые форматы;
* получение внешних ссылок;
* операции, специфичные для источника.

Добавление нового источника не должно требовать изменения модели проекта.

## TrackLibrary

`TrackLibrary` является центральным состоянием рабочей области.

Он управляет:

* источниками;
* метаданными;
* активным объектом;
* видимостью и порядком;
* очередью загрузки;
* ошибками загрузки.

Такое сосредоточение ответственности является осознанным упрощением и не требует автоматического разделения на сервисы.

---

# UI и карта

UI отвечает за отображение данных и пользовательское взаимодействие.

UI не должен:

* выполнять предметные вычисления;
* рассчитывать характеристики геометрии;
* принимать бизнес-решения;
* разбирать внешние форматы;
* знать детали внешних API.

Форматирование данных для отображения допускается, если оно не изменяет предметный смысл данных и не дублирует вычисления модели.

Повторяющиеся визуальные элементы и шаблоны взаимодействия должны выделяться в переиспользуемые компоненты после появления устойчивого повторения.

Переиспользование не должно приводить к созданию универсальных компонентов с большим количеством режимов и условных ветвей.

Карта рассматривается как крупная изолированная зона интерфейса.

Она отвечает за отображение треков, слоёв, подписей, рельефа и событий взаимодействия, но не принимает бизнес-решений.

---

# Организация кода внутри слоя

Код внутри слоя должен группироваться по ответственности и причинам изменения.

Код, который изменяется совместно, должен находиться рядом.

Модули должны стремиться к высокой связности.

Не следует создавать дополнительные уровни вложенности, папки или файлы без самостоятельной ответственности.

Предпочтительно небольшое число крупных и понятных модулей, чем множество мелких сущностей без ясной роли.

---

# Правило размещения логики

Если функция отвечает на вопрос:

* «что можно вычислить по геоданным?» — это `model`;
* «как прочитать или записать формат?» — это `formats`;
* «как работать с внешней системой?» — это интеграция;
* «как перевести внешние данные в модели проекта?» — это `TrackSource`;
* «как выполнить пользовательский сценарий?» — это `application`;
* «как показать данные пользователю?» — это `ui`.

---

# Компромиссы и развитие

Текущая структура проекта является применением принципов на данном этапе, а не вечным правилом.

Если решение перестаёт соответствовать принципам, меняется решение, а не принцип.

Архитектурные компромиссы допускаются, если они упрощают систему и локализуют сложность.

Известные компромиссы:

* связь `TrackMeta` ↔ `TrackSource`;
* возможное дублирование между `src/komoot` и `api/komoot`.

---

# Безопасность и данные

* локальные файлы обрабатываются в браузере и не отправляются на сервер;
* секреты внешних систем не попадают в клиентский код;
* серверные proxy ограничиваются поддерживаемыми API;
* исходные пользовательские данные не изменяются без явного действия пользователя.
