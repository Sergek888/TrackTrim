# Agent instructions

## Required context

Перед началом работы прочитай:

- `docs/product.md`;
- `docs/architecture.md`;
- `docs/roadmap.md`.

Затем изучи код, относящийся к текущей задаче, и проверь состояние рабочего дерева через `git status`.

## Sources of truth

- `docs/product.md` описывает назначение продукта, текущий объём и пользовательские сценарии.
- `docs/architecture.md` определяет границы модулей, направление зависимостей и правила размещения кода.
- `docs/roadmap.md` определяет текущие приоритеты, когда roadmap заполнен.
- Исходный код отражает фактически реализованное поведение.

Если документация и код противоречат друг другу, явно сообщи о расхождении. Не исправляй его молча и не выбирай одну сторону без обоснования.

## Working principles

- Выполняй минимальный согласованный объём изменений.
- Не меняй несвязанный код, структуру проекта и архитектурные границы без отдельного обоснования и подтверждения.
- Сохраняй существующие соглашения и подходы проекта.
- Не создавай новые сущности и абстракции без необходимости.
- Не добавляй зависимости, если задачу можно решить существующими средствами.
- Не выполняй попутный рефакторинг вне текущей задачи.

## Workflow

1. Проанализируй требования, документацию и относящийся к задаче код.
2. Опиши:
   - какие файлы будут изменены;
   - зачем они будут изменены;
   - что останется нетронутым;
   - какие проверки будут выполнены.
3. Получи явное подтверждение предложенного объёма.
4. Измени только согласованные файлы.
5. Выполни подходящие проверки.
6. Проверь итоговый `git diff` и `git status`.
7. Кратко опиши результат, выполненные проверки и известные ограничения.
8. Оформи завершённую доработку отдельным Git-коммитом.

## Change approval

- Не вноси изменения до явного подтверждения конкретного шага.
- Не расширяй согласованный объём без дополнительного обсуждения.
- Если в процессе обнаружена необходимость изменить другие файлы или архитектурную границу, сначала объясни причину и запроси подтверждение.
- Анализ и предложения не требуют изменения файлов.

## Verification

- Выполняй наиболее узкую достаточную проверку для изменённого поведения.
- Для изменений TypeScript/React по умолчанию выполняй `npm run build`.
- При наличии тестов запускай тесты, относящиеся к изменению.
- Для изменений UI по возможности проверяй изменённый сценарий в браузере.
- Если проверку выполнить невозможно, явно укажи причину.
- Не объявляй задачу завершённой при ошибках проверки без описания ошибки и её последствий.

## Architecture safeguards

- Соблюдай правила размещения кода из `docs/architecture.md`.
- Не добавляй специфику внешней системы в `Track`, `TrackLibrary` или общие UI-компоненты.
- Новая внешняя интеграция должна состоять из изолированной интеграционной библиотеки и проектного `TrackSource`-адаптера.
- Локальные GPX/XML-файлы не должны отправляться на сервер.
- Не мутируй исходный `Track` и исходные локальные файлы.
- Не помещай предметную логику в общий helper.

## Documentation

- Обновляй документацию, если изменение затрагивает публичное поведение, текущий объём продукта или архитектурную границу.
- Разделяй фактическую реализацию, целевую архитектуру и будущие возможности.
- Будущий функционал явно помечай как будущий.
- Не добавляй возможности в roadmap автоматически: roadmap обновляется только в рамках отдельного согласованного изменения.
- Не дублируй подробное содержание `product.md` и `architecture.md` в `AGENTS.md`.

## Git rules

- Не изменяй и не откатывай существующие незакоммиченные изменения, не относящиеся к задаче.
- Перед коммитом проверь `git diff` и `git status`.
- Включай в коммит только файлы текущей задачи.
- Не используй destructive-команды Git без явного запроса.
- Не выполняй push без явного запроса.
- Не переписывай историю Git без явного запроса.

## Ambiguous requirements

Если требования существенно неоднозначны:

1. Перечисли варианты.
2. Объясни последствия и компромиссы каждого варианта.
3. Рекомендуй один вариант.
4. Не угадывай и не начинай рискованные или необратимые изменения без ответа.

Не запрашивай уточнение, если ответ однозначно следует из кода или документации.

## Completion report

После изменений кратко укажи:

- что изменено;
- какие файлы затронуты;
- что проверено;
- что не удалось проверить;
- идентификатор созданного коммита.
