# Architecture

## Main principle

Track — основная модель геометрии GPS-трека.

GPX, Komoot и будущие внешние системы являются способами получения или сохранения данных, но не частью модели Track.

Основной поток:

```text
External data
→ integration or format adapter
→ TrackSource
→ TrackMeta / Track
→ TrackLibrary
→ UI
```

Поток локального файла:

```text
File
→ LocalFileTrackSource
→ GpxConverter
→ Track
→ TrackLibrary
→ UI
```

Поток внешней системы:

```text
External system library
→ TrackSource adapter
→ TrackMeta / Track
→ TrackLibrary
→ UI
```

## Modules

```text
src/
    model/
    formats/
    application/
    komoot/
    ui/

api/
    komoot/
```

## Dependency direction

Предпочтительное направление зависимостей:

```text
ui
→ application
→ model

application sources
→ formats
application sources
→ external integration libraries

formats
→ model data contracts

external integration libraries
→ own DTO and transport contracts
```

Внешняя интеграционная библиотека не должна зависеть от `Track`, `TrackMeta`, `TrackSource`, `formats`, `application` или `ui`.

Адаптация внешних DTO к моделям проекта выполняется реализацией `TrackSource` в слое `application`.

## Model

`model`:

- содержит явные представления реально существующих сущностей предметной области, их состояния и поведения;
- содержит `Track`, `TrackPoint`, `TrackStatistics`, `TrackInterval` и связанные параметры;
- содержит универсальные вычисления по треку;
- рассчитывает расстояние, длительность, скорость и набор высоты;
- хранит для каждой точки накопленное расстояние и время от начала;
- умеет находить ближайшую точку;
- создаёт производные сегменты Track;
- может выполнять универсальную сегментацию и анализ данных;
- не знает о GPX, XML, HTTP, Komoot, UI или пользовательских сценариях.

Если понятие воспроизводит реально существующую сущность предметной области, оно должно быть явно представлено в `model`, а не скрыто в UI-состоянии, helper, транспортном DTO или application-сервисе.

Модель должна отражать предметный смысл, а не структуру экрана, формат внешнего ответа или удобство конкретной реализации. Технические объекты, не имеющие самостоятельного предметного смысла, не становятся сущностями модели.

### Track immutability

- набор точек Track не изменяется после создания;
- операции выделения части трека создают новый Track;
- производный Track сохраняет тот же `TrackMeta`, если не требуется иное;
- исходный Track не должен изменяться при отображении, анализе или экспорте.

### TrackMeta

`TrackMeta` является паспортом трека в источнике:

- содержит имя, цвет, видимость и состояние загрузки;
- содержит идентификатор трека во внешнем источнике;
- связывает Track с живым экземпляром `TrackSource`;
- делегирует получение оригинальной и публичной ссылки источнику;
- может существовать до загрузки геометрии Track.

Связь `TrackMeta` с `TrackSource` является осознанным компромиссом текущей архитектуры. Она позволяет сохранять поведение живого источника рядом с метаданными, но создаёт зависимость модели метаданных от application-контракта.

## Formats

`formats`:

- читает и пишет внешние файловые форматы;
- преобразует внешний payload в `TrackPointInput[]`;
- преобразует точки Track обратно во внешний payload;
- не создаёт пользовательских сценариев;
- не управляет источниками;
- не принимает решения о загрузке или отображении.

### TrackConverter

`TrackConverter` задаёт общий контракт преобразования:

```text
RawPayload
→ ParsedGeometry

TrackPointInput[]
→ RawPayload
```

`GpxConverter` является текущей реализацией для GPX.

## Application

`application` оркестрирует пользовательские сценарии и связывает модель с источниками.

### TrackSource

`TrackSource` представляет источник треков и отвечает за:

- загрузку списка `TrackMeta`;
- загрузку Track по метаданным;
- экспорт Track в поддерживаемый формат;
- получение оригинальной и публичной ссылки;
- имя, цвет, видимость, состояние раскрытия и порядок источника.

Текущие реализации:

- `LocalFileTrackSource` — локальные GPX/XML-файлы;
- `KomootTrackSource` — адаптер между Komoot-библиотекой и моделями TrackTrim.

Будущая интеграция с другой системой должна добавляться как:

```text
isolated integration library
+ TrackSource adapter
```

Добавление нового источника не должно требовать изменения `Track`.

### TrackLibrary

`TrackLibrary` является прикладным хранилищем состояния рабочей области.

Она отвечает за:

- список и порядок источников;
- список `TrackMeta`;
- активный и сфокусированный трек;
- видимость и цвет источников и треков;
- переименование и удаление источников;
- уведомление UI об изменениях;
- очередь загрузки геометрии;
- приоритет активного трека;
- ограничение числа параллельных загрузок;
- ошибки загрузки.

`TrackLibrary` не должна разбирать внешние форматы и самостоятельно выполнять HTTP-запросы.

## Komoot integration library

`src/komoot` рассматривается как изолированная внутренняя библиотека интеграции с Komoot, а не как слой бизнес-логики TrackTrim.

Библиотека отвечает за:

- разбор Komoot URL и идентификаторов;
- собственные DTO;
- вызовы Komoot API;
- получение метаданных и координат;
- транспортные ошибки;
- прямой и серверный транспорт;
- разбор ответов Komoot.

Библиотека не должна:

- создавать `Track`, `TrackMeta` или `TrackSource`;
- знать о структуре UI;
- принимать решения о видимости, цвете или порядке треков;
- управлять библиотекой TrackTrim;
- содержать пользовательские сценарии проекта.

`KomootTrackSource` находится в `application` и адаптирует DTO Komoot к `TrackMeta`, `TrackPointInput` и `Track`.

## Server runtime for Komoot

`api/komoot` — текущее серверное окружение Komoot-интеграции для Vercel.

Оно предоставляет:

- HTTP endpoints;
- обмен логина и пароля на Komoot API-сессию;
- серверное хранение сессии;
- `HttpOnly` cookie TrackTrim;
- ограниченный proxy к разрешённым Komoot API;
- адаптацию запросов и ответов к Vercel runtime.

Этот каталог не должен становиться второй независимой реализацией Komoot-интеграции. Общие правила, DTO и разбор внешних ответов должны по возможности оставаться в изолированной библиотеке, а runtime-код должен быть тонким серверным адаптером.

Текущий код частично дублирует клиентскую Komoot-библиотеку. Это известный архитектурный долг, а не целевая граница.

## UI

`ui`:

- является максимально тонким слоем отображения и пользовательского ввода;
- отображает состояние `TrackLibrary`;
- создаёт пользовательские события;
- не разбирает GPX или ответы внешних API;
- не выполняет вычисления модели вручную;
- не содержит предметных вычислений, правил принятия решений или преобразований, принадлежащих `model`, `application`, `formats` или интеграционной библиотеке;
- не изменяет точки существующего Track;
- получает готовые данные через props и application-контракты.

Контейнерные компоненты могут связывать UI с `TrackLibrary` и источниками, но не должны становиться местом предметной логики. Presentational-компоненты получают готовые данные и callbacks.

Повторяющийся визуальный элемент, шаблон взаимодействия или фрагмент поведения интерфейса должен быть выделен в повторно используемый UI-компонент, когда повторение уже существует и компонент имеет ясную ответственность. Переиспользование не должно приводить к универсальным компонентам с большим числом несвязанных режимов и условных ветвей.

Форматирование данных для отображения может находиться в `ui`, если оно не изменяет предметный смысл данных и не дублирует вычисления модели.

## Map

Карта находится только в `ui`.

`TrackMap`:

- получает готовые Track;
- преобразует их в GeoJSON через UI-адаптер;
- отображает несколько треков;
- выделяет активный трек;
- показывает маркеры начала и конца;
- управляет базовыми слоями, подписями и рельефом;
- генерирует события выбора и фокусировки;
- не загружает источники;
- не разбирает внешние форматы;
- не принимает бизнес-решения;
- не создаёт и не изменяет Track.

## External integrations

Интеграции с внешними системами должны следовать общей схеме:

```text
External API
→ isolated integration library
→ application TrackSource adapter
→ TrackMeta / Track
```

Изолированная библиотека должна быть пригодна для использования без специфики TrackTrim. Проектный адаптер отвечает за перевод её DTO в модели приложения.

Новая интеграция не должна добавлять условные ветви конкретной системы в `Track`, `TrackLibrary` или общие UI-компоненты.

## Future analysis and editing

Анализ и редактирование являются возможным будущим функционалом, а не текущей целью архитектуры.

Если такие сценарии будут добавлены, общий поток должен выглядеть так:

```text
Track
→ application operation
→ preview Track
→ user confirmation
→ resulting Track
→ source export
```

При этом:

- вычисления по геометрии остаются в `model`;
- пользовательский сценарий и подтверждение находятся в `application`;
- UI только отображает preview и собирает действия пользователя;
- исходный Track не мутируется;
- внешние форматы используются только на границах чтения и экспорта.

## Placement rules

Если функция отвечает на вопрос «что можно вычислить по треку?», она относится к `model`.

Если функция отвечает на вопрос «как выполнить пользовательский сценарий?», она относится к `application`.

Если функция отвечает на вопрос «как прочитать или записать формат?», она относится к `formats`.

Если функция отвечает на вопрос «как взаимодействовать с конкретной внешней системой?», она относится к изолированной библиотеке этой интеграции.

Если функция отвечает на вопрос «как перевести данные внешней системы в модели проекта?», она относится к адаптеру `TrackSource` в `application`.

Если функция отвечает на вопрос «как показать данные пользователю?», она относится к `ui`.

## Architecture decision principles

### Minimal number of entities

- Количество классов, интерфейсов, сервисов, адаптеров и файлов не является показателем качества архитектуры.
- Не следует создавать новую сущность только для переноса кода в отдельный файл или уменьшения размера существующего класса.
- Если поведение естественно относится к существующей сущности и не нарушает её ответственность, оно должно оставаться в ней.
- Новая сущность должна иметь самостоятельный смысл, устойчивую ответственность и ясную границу.
- Перед добавлением сущности необходимо проверить, нельзя ли решить задачу существующей моделью или контрактом без нарушения их ответственности.

### New entities after critical analysis

Новая сущность или архитектурная граница предлагается только после критического анализа, который показывает, что поведение не вписывается в существующие сущности.

Перед созданием новой сущности необходимо установить:

1. Поведение не относится к существующей сущности.
2. Размещение поведения в существующем модуле нарушит его ответственность.
3. Поведение имеет собственный устойчивый предметный или технический смысл.
4. Новая граница уменьшит реальную связанность, локализует изменчивость или устранит подтверждённое дублирование.
5. Координационный код и новые зависимости не окажутся сложнее решаемой проблемы.

Если эти условия не выполняются, новая сущность не создаётся.

### Simple architecture

- Следует выбирать самое простое решение, сохраняющее корректные границы ответственности.
- Не следует вводить новый слой, паттерн или инфраструктуру ради возможного будущего использования.
- Не следует создавать фабрики, реестры, контейнеры, event bus, универсальные pipeline и другие посредники без существующей задачи, которую они явно упрощают.
- Прямой вызов между слоями с разрешённой зависимостью предпочтительнее цепочки посредников без самостоятельной ответственности.
- Архитектурная сложность допустима, только если она изолирует реальную изменчивость, защищает важную границу или заметно упрощает развитие системы.

### Layer separation

- Слои разделяются по ответственности и причинам изменения, а не по технической форме кода.
- Отдельный файл, интерфейс или wrapper сам по себе не создаёт архитектурную границу.
- Полезная граница позволяет одной стороне изменяться без знания внутренних деталей другой стороны.
- Не следует создавать слой, который только перенаправляет вызовы и не владеет отдельным поведением или политикой.
- Предметная модель, пользовательские сценарии, внешние форматы, транспорт, состояние рабочей области и отображение не должны смешиваться.

### Do not hide coupling

- Дополнительный интерфейс не устраняет связанность, если стороны продолжают знать внутренние детали друг друга.
- Dependency injection, callbacks, события и промежуточные сервисы не должны использоваться только для сокрытия прямой зависимости.
- Если два модуля всегда изменяются совместно по одной причине, их искусственное разделение может увеличить, а не уменьшить связанность.
- Если модуль знает структуру DTO, правила ошибок и жизненный цикл другой стороны, формальное наличие интерфейса ещё не означает изоляцию.
- Связанность должна быть либо признана и локализована, либо устранена изменением ответственности, а не замаскирована дополнительными уровнями вызовов.

### Abstractions from real cases

- Общий контракт не проектируется по одной реализации и гипотетическим будущим требованиям.
- Абстракция создаётся после появления устойчивого общего поведения или подтверждённой точки изменчивости.
- Различия конкретных источников остаются в их интеграционных библиотеках и адаптерах, пока для них не возникнет реальная общая модель.
- Не следует добавлять параметры, режимы и условные ветви в общий контракт ради одной реализации.
- Несколько прямых и понятных реализаций предпочтительнее преждевременной универсальной системы.

### Responsibility and decomposition

- Размер модуля сам по себе не является причиной для его разделения.
- Разделение необходимо, когда у модуля появляются независимые ответственности или разные причины изменения.
- Последовательный алгоритм не следует дробить на множество сущностей, если это скрывает основной поток и усложняет понимание.
- Техническую деталь можно вынести в узкий модуль, не превращая этот модуль в новый архитектурный слой.
- Helper допустим только для небольшой технической операции без самостоятельного предметного смысла.
- Helper не является самостоятельным архитектурным слоем и не должен становиться местом для несвязанной логики.

### Localize changes

- Новая возможность должна требовать изменений в минимальном числе существующих модулей.
- Специфика одной реализации не должна расширять общий контракт без необходимости.
- Добавление нового источника не должно требовать изменения `Track`, `TrackLibrary` и общих UI-компонентов.
- Если простое изменение требует согласованного редактирования многих слоёв, необходимо проверить правильность существующих границ.

### Architecture change criteria

Перед усложнением архитектуры необходимо ответить:

1. Какую конкретную существующую проблему решает изменение?
2. Какая ответственность или граница становится яснее?
3. Какая реальная связанность уменьшается?
4. Какие будущие изменения локализуются благодаря новой границе?
5. Какова стоимость новой сущности, контракта и координационного кода?
6. Можно ли решить задачу проще без нарушения архитектурных правил?

Если ответы не показывают явной пользы, архитектурное усложнение не выполняется.

## Security and data handling

- локальные GPX/XML-файлы читаются в браузере;
- локальные файлы не отправляются на сервер;
- пароль Komoot используется только для создания API-сессии и не сохраняется;
- браузер хранит только идентификатор TrackTrim-сессии в `HttpOnly` cookie;
- Komoot API token хранится на серверной стороне;
- server proxy разрешает запросы только к поддерживаемым Komoot API;
- исходные локальные файлы не изменяются.
