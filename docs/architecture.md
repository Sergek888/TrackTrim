# Архитектура TrackViewer

## Назначение

TrackViewer — приложение для работы с геоданными независимо от их источника, формата и способа отображения.

Архитектура строится вокруг связки:

```text
геоданные → рабочая область → карта → действия пользователя
```

Конкретные сущности могут меняться: `Track`, маршрут, коллекция, анализ, слой карты, внешний источник. Архитектурные принципы должны оставаться стабильными.

## Основной поток данных

```text
External data → integration or format adapter → TrackSource → TrackMeta / Track → TrackLibrary → UI
```

Локальные файлы:

```text
File → LocalFileTrackSource → GpxConverter → Track → TrackLibrary → UI
```

Внешние системы:

```text
External API → integration library → TrackSource adapter → TrackMeta / Track → TrackLibrary → UI
```

## Основные принципы

### Предметная модель независима от источников

Внешние системы, форматы файлов, API и UI не определяют устройство предметной модели. Внешние данные адаптируются к модели проекта, а не наоборот.

### Крупные зоны ответственности изолируются

Проект разделяется на независимые области: предметная модель, файловые форматы, внешние интеграции, рабочая область, карта и UI, серверные runtime-адаптеры.

Изменение GPX не должно требовать изменения Komoot. Изменение карты не должно требовать изменения модели. Добавление нового источника не должно требовать изменений в общих UI-компонентах.

### Границы строятся по причинам изменения

Модуль выделяется тогда, когда у него появляется собственная причина изменяться. Размер файла, количество строк или желание «навести порядок» сами по себе не являются причиной для создания новой сущности.

### Простота важнее формальной чистоты

Один понятный модуль лучше нескольких абстракций без самостоятельной ответственности. Не следует вводить новые слои, сервисы, фабрики, registry, event bus или универсальные pipeline без существующей задачи.

### Не скрывать связанность

Интерфейс или промежуточный слой не устраняют связанность сами по себе. Если модули знают внутренние детали друг друга и изменяются совместно, искусственное разделение может увеличить сложность.

### Новая сущность появляется под давлением задачи

Новая сущность или архитектурная граница создаётся только если поведение не относится к существующей сущности, существующий модуль нарушает ответственность, новая граница локализует изменчивость или устраняет реальное дублирование.

### Универсальность и рост

Общие интерфейсы и контракты создаются на основе реальных сценариев. Абстракция создаётся после появления устойчивого повторения. Простая реализация предпочтительнее преждевременной универсальности.

## Направление зависимостей

```text
ui → application → model
application → formats / integrations
formats → model data contracts
integrations → own DTO and transport contracts
```

Запрещённое направление важнее структуры каталогов.

- `model` не зависит от UI, HTTP, форматов и внешних сервисов;
- `formats` не зависят от UI и пользовательских сценариев;
- интеграции не зависят от UI и внутреннего состояния приложения;
- UI не содержит предметных вычислений.

## Model

`model` содержит предметную модель и универсальные вычисления по геоданным.

Она может рассчитывать расстояние, длительность, скорость и набор высоты; хранить накопленные значения; находить ближайшие точки; создавать сегменты и производные объекты; выполнять универсальный анализ геометрии.

`model` не знает о GPX, XML, HTTP, Komoot и UI.

### Track

`Track` является неизменяемым. Точки не изменяются после создания. Анализ, сегментация и будущие операции редактирования создают новый `Track`. Исходный объект не мутируется.

### TrackPoint

`TrackPoint` различает абсолютное время `time` и время от начала `elapsedSec`. Расчёты длительности и скорости используют `elapsedSec`. Производный `Track` перенормирует elapsed-время относительно своей первой точки. Форматы экспортируют только настоящее абсолютное время и не превращают elapsed-значения во временные метки Unix epoch.

### TrackMeta

`TrackMeta` является паспортом объекта во внешнем источнике и единственным контрактом отображаемых характеристик для общего UI.

```text
source response → TrackSource → Track → prepared TrackMeta → UI
```

`TrackSource` переводит внешние значения в закрытые предметные типы и сохраняет их в `TrackMeta`. После создания `Track` источник может заполнить расчётами только пустые поля базовых характеристик. Значения, уже предоставленные источником, не перезаписываются.

Компоненты UI форматируют готовые значения, но не вызывают аналитические методы `Track` для получения характеристик.

Связь `TrackMeta` с `TrackSource` является осознанным компромиссом текущей архитектуры.

## Formats

`formats` отвечают только за чтение и запись внешних форматов. Они преобразуют данные формата в модели проекта и обратно. Форматы не управляют отображением, загрузкой или пользовательскими сценариями.

Текущая реализация: `GpxConverter`.

## Integrations

Интеграция с внешней системой должна состоять из integration library и `TrackSource` adapter.

Интеграционная библиотека отвечает за API, DTO, transport, authorization, errors и особенности внешней системы. Она не должна знать о UI, `TrackLibrary` или внутренней структуре приложения.

### Komoot

`src/komoot` является единственным владельцем Komoot API, DTO, разбора ответов и fallback-стратегий.

Библиотека разделена по ответственностям: `auth`, `users`, `tours`, `collections`, `mutations`, `import`, `url`, `normalize`, `transport`, `shared`, `KomootApiClient`.

`KomootApiClient` является точкой сборки и предоставляет фасад публичных возможностей интеграции.

Транспорт библиотеки не знает адресов серверных маршрутов приложения. Application-адаптеры, включая `KomootTrackSource`, зависят только от публичного контракта библиотеки.

## Server runtime adapters

`api/komoot` содержит только серверные runtime-адаптеры: создание и удаление Komoot-сессии, проверку состояния сессии, ограниченный авторизованный proxy, отдельные POST routes для upload, edit и delete.

Серверный runtime не нормализует туры и коллекции и не реализует параллельный прикладной Komoot API. Mutation-запросы через общий proxy запрещены.

Komoot API tokens перед записью в session store шифруются посредством AES-256-GCM. Ключ выводится из обязательного `KOMOOT_SESSION_SECRET` длиной не менее 32 символов. Legacy plaintext sessions считаются истёкшими.

## Application

`application` связывает модель, форматы, интеграции и UI. Здесь находятся пользовательские сценарии, `TrackSource` и `TrackLibrary`.

UI получает готовое состояние и вызывает прикладные операции, не зная HTTP endpoints и transport DTO.

### TrackSource

`TrackSource` представляет источник данных и отвечает за загрузку списка объектов, загрузку геометрии, экспорт, получение внешних ссылок и операции источника.

Добавление нового источника не должно требовать изменения модели проекта.

### TrackLibrary

`TrackLibrary` является центральным состоянием рабочей области. Он управляет источниками, метаданными, активным объектом, видимостью и порядком, очередью загрузки и ошибками загрузки.

Такое сосредоточение ответственности является осознанным упрощением и не требует автоматического разделения на сервисы.

## UI и карта

UI отвечает за отображение данных и пользовательское взаимодействие.

UI не должен выполнять предметные вычисления, рассчитывать характеристики геометрии, принимать бизнес-решения, разбирать внешние форматы или знать детали внешних API.

Форматирование данных для отображения допускается, если оно не изменяет предметный смысл данных и не дублирует вычисления модели.

Карта рассматривается как крупная изолированная зона интерфейса. Она отвечает за отображение треков, слоёв, подписей, рельефа и событий взаимодействия, но не принимает бизнес-решений.

## Организация кода внутри слоя

Код внутри слоя должен группироваться по ответственности и причинам изменения. Код, который изменяется совместно, должен находиться рядом. Не следует создавать дополнительные уровни вложенности, папки или файлы без самостоятельной ответственности.

## Правило размещения логики

- «что можно вычислить по геоданным?» — `model`;
- «как прочитать или записать формат?» — `formats`;
- «как работать с внешней системой?» — integration;
- «как перевести внешние данные в модели проекта?» — `TrackSource`;
- «как выполнить пользовательский сценарий?» — `application`;
- «как показать данные пользователю?» — `ui`.

## Компромиссы и развитие

Текущая структура проекта является применением принципов на данном этапе, а не вечным правилом. Если решение перестаёт соответствовать принципам, меняется решение, а не принцип.

Известные компромиссы: связь `TrackMeta` с `TrackSource`; сосредоточение состояния рабочей области в `TrackLibrary`; временная стратегия заполнения пустых базовых характеристик `TrackMeta`.

## Безопасность и данные

- локальные файлы обрабатываются в браузере и не отправляются на сервер;
- секреты внешних систем не попадают в клиентский код;
- серверные proxy ограничиваются поддерживаемыми API;
- исходные пользовательские данные не изменяются без явного действия пользователя.
